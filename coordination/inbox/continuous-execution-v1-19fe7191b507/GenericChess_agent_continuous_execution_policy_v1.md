# GenericChess Agent Continuous Execution Policy v1

## Status

This is a persistent execution policy for Agent work on GenericChess.

It applies to all current and future inbox TASK / AUDIT artifacts unless a later artifact explicitly overrides it.

This policy exists because incremental checkpoints, pushes, audits, or intermediate successes are **not** intended to return control to the user.

---

# 1. Core hard rule

When Agent consumes an inbox TASK, it MUST continue executing the task in one continuous run until one of these two conditions is true:

1. **The task's full completion criteria are satisfied**, including all requested implementation, debugging, tests, validation, pushes, and final report; or
2. **A genuine hard blocker prevents further progress**, and Agent has exhausted reasonable local attempts to resolve it.

Anything else is not a valid stopping point.

In particular, Agent MUST NOT stop merely because:

- a phase completed;
- a checkpoint was committed;
- a checkpoint was pushed;
- a build became green;
- a focused test suite passed;
- a design decision was made;
- a public API was added;
- a first differential test passed;
- a milestone was reached;
- the next phase looks larger or riskier;
- Chat has not yet audited the latest SHA;
- Chat has not yet replied;
- there may be future audit feedback;
- the task is long;
- a useful status update can be written.

A checkpoint means:

> **commit + push + continue**

not:

> commit + push + stop and wait.

---

# 2. User/Chat intent has priority

If an inbox TASK contains multiple phases, that means the user and Chat intentionally authorized Agent to execute those phases continuously.

Agent MUST NOT reinterpret a long prompt as:

> “Do the first safe-looking subsection and then ask again.”

The correct interpretation is:

> “Execute the entire authorized scope unless a real blocker makes further work impossible.”

If Chat believed a boundary required mandatory human approval, the TASK would explicitly say:

```text
STOP HERE AND WAIT FOR APPROVAL
```

Without that exact or equivalent instruction, do not invent an approval gate.

---

# 3. Checkpoints are asynchronous audit points, not barriers

Agent is encouraged to create clean incremental commits and push them to `origin/sandbox`.

However:

- pushing a checkpoint does not pause implementation;
- Chat may audit older pushed SHAs while Agent works ahead;
- an audit is SHA-bound;
- later work does not invalidate the usefulness of an older audit;
- Agent does not wait for Chat before continuing unless the TASK explicitly requires a synchronous gate.

Normal behavior:

```text
implement
→ test
→ commit checkpoint A
→ push checkpoint A
→ continue immediately
→ implement more
→ test
→ commit checkpoint B
→ push checkpoint B
→ continue
```

Chat can independently audit A or B in parallel.

---

# 4. Inbox AUDIT handling

At natural safe boundaries, Agent should run the bridge sync and inspect newly arrived AUDIT artifacts.

This is not a reason to stop.

If an AUDIT says PASS:

```text
record PASS
→ continue current TASK
```

If an AUDIT says FAIL:

```text
integrate findings
→ fix
→ test
→ new commit/SHA
→ push
→ continue current TASK
```

If the FAIL concerns an older checkpoint while Agent has already changed adjacent code:

- apply the finding to the current codebase;
- verify the issue is actually closed in current HEAD;
- add/adjust regression tests;
- do not reset valuable later work merely to recreate the old checkpoint.

Only stop if the audit reveals a true architecture conflict that cannot be resolved without a decision outside the authority already granted by the TASK.

---

# 5. Valid hard blockers

A “hard blocker” must be concrete.

Examples that may justify stopping:

- required credential does not exist and cannot be generated by Agent;
- OS permission requires explicit human/admin interaction and no safe fallback exists;
- required external service is unavailable and no local substitute can validate the task;
- repository state is inconsistent in a way that makes continuing destructive;
- the task requires a product decision for which multiple incompatible choices are equally plausible and the TASK did not grant discretion;
- a safety/security boundary explicitly requires human action;
- the requested goal is technically impossible under the current architecture and Agent can demonstrate why.

Before stopping on a blocker, Agent MUST:

1. attempt reasonable diagnosis;
2. attempt safe local recovery;
3. search existing repo/docs/tests for authority;
4. preserve all valid work;
5. push useful non-broken checkpoints if possible;
6. report exact evidence, not a vague concern.

Not valid blockers:

- “this is a big next step”;
- “I want Chat to review first”;
- “a checkpoint seems like a natural pause”;
- “tests are green so I will report progress”;
- “I have completed Phase A and will do Phase B next”;
- “I need to think about architecture” when the TASK already grants design discretion;
- ordinary bugs;
- compiler errors;
- failing tests;
- refactoring needs;
- uncertainty that can be resolved by reading code/tests.

Those are normal engineering work. Continue.

---

# 6. Failure is work, not a stop signal

Compiler failures, crashes, differential mismatches, test regressions, and malformed-state failures are expected during implementation.

Default reaction:

```text
failure
→ diagnose
→ fix
→ add regression
→ rerun
→ continue
```

Do not return control to the user just because something failed once.

---

# 7. Sandbox authority

`sandbox` is the engineering workspace.

Within the scope of the current TASK, Agent may freely:

- edit;
- refactor;
- add files;
- add tests;
- build;
- debug;
- commit;
- push multiple checkpoints.

Do not become conservative merely because a change might later fail audit.

If a sandbox implementation is wrong, Chat will audit it and Agent will fix it.

The cleanliness requirement applies to promotion into `master`, not to avoiding ambitious work in `sandbox`.

Do not merge `master` unless explicitly authorized.

Do not force-push.

Do not contaminate a future master candidate with `coordination/` or unrelated artifacts.

---

# 8. Reporting behavior

Intermediate progress may be recorded in commits/logs, but Agent should not terminate the run merely to send a progress report.

For a one-shot inbox TASK, the expected user-facing response is normally only one of:

## A. Final completion report

All requested phases are complete.

Report:
- actual SHAs;
- tests;
- architecture;
- remaining non-blocking limitations;
- worktree status.

## B. Hard-blocker report

Further progress is genuinely impossible.

Report:
- exact blocker;
- evidence;
- attempted fixes;
- last good SHA;
- remaining work;
- exact human action required, if any.

Avoid responses of the form:

> “Phase A is done. Next I will implement Phase B.”

If Phase B is authorized, implement Phase B now.



---

# 11. Final invariant

The default control-flow invariant is:

```text
TASK RECEIVED
    ↓
EXECUTE
    ↓
BUG / TEST FAIL / CHECKPOINT / PUSH / AUDIT
    ↓
CONTINUE
    ↓
COMPLETE
```

Only a true hard blocker may replace `CONTINUE` with `STOP`.

A checkpoint is evidence for parallel audit, not permission to stop.
