## Cost, histories and actual consumers

The 384-query encoding family passes the 20% player-plus-query cost gate in
10/12 cases. Adding shared rule compilation as a hypothetical cold cost lowers
that to 8/12. That estimate excludes strict record replay: the earlier private
label “complete cold” was imprecise and is corrected here. A new randomized
96-call fresh-rule/replay/player/serialization comparison passes in 10/12 cases;
all semantic pairs agree. These are correlated repeated observations, not
independent confidence intervals or a utility experiment.

Four real continuing histories reach prefixes 0/16/64/128 without truncation.
All 128 queries finish D2 and matched results agree. Those roots have different
physical positions, so changes in query speed cannot be attributed to history
length alone. A separate new repetition-64 rule fixes the entire physical
position after real king loops; it does not extend any old frozen rule/cap.
All 32 controls have the same action, score, PV and **22 nodes**; complete count
maps remain different and genuine. Each search imports all 5/17/65/129 witnesses.

Common replay cost dilutes a query saving: with common setup C, profile P,
serialization S, Core query Q, provider setup K and Native query N, the ratio is
`(C+P+K+N+S)/(C+P+Q+S)`. Increasing C drives the ratio toward 1. This does not
justify discarding history. Retained-session timings also contain a real
prefix-16 regression: Native query 13.069ms versus 4.239ms on its repeat, with the
same 22 nodes, 50 pushes and 11 Native calls. Its cause is unestablished; neither
that observation nor the failed cost gate was removed or rerun for improvement.

The maintained benchmark creates one GameSession and repeatedly calls
`choose_action(session, limits)` before submission. AlphaBetaPlayer passes its
existing search witnesses. SearchSnapshot is an envelope over the existing
session, not serialized reconstruction. This is source review, not execution of
the user's UI. No per-turn replay cache or replacement API is justified for the
inspected caller. External cold-record and continuing-session cost remain distinct.

## History-key alternative and primary literature

Two actually played plain-draw loops in swapped order have the same full
position/ply/count map but different chronological histories. A private gated
key projection permits warm reuse: 149 to 8 nodes at the same D4 score 995.
It explicitly retains long-check distinction and excludes automatic, consecutive,
cycle-target and no-progress adjudication. In the ordinary 96-query panel,
44/48 pairs complete the requested depth with equal action/score; all four
incomplete pairs remain. There is no aggregate benefit. A fresh 144-query D3
trial also skips the unnecessary order digest only in that private plain-rule
scope: every action/score/PV matches, but ratios 0.974–0.994 fail the 20% gate
in all six fixtures. Do not implement a history-key/digest rewrite from the
special warm witness. An attempted history-reading evaluator counterexample
failed because RuntimeSearchState exposes no public history attribute; no API
expansion or private-field escape was used to rescue it.

[Kishimoto and Müller, AAAI 2004](https://cdn.aaai.org/AAAI/2004/AAAI04-102.pdf)
was read through the official full text after earlier author-host retrieval
failures. Its method rechecks path-dependent proofs through simulation and keeps
proven/disproven evidence; its stated guarantee is not a guarantee for arbitrary
heuristic values or replacement in a bounded table. GenericChess has not
implemented that method. The limited plain-rule experiment does not establish
that arbitrary relevant histories can be collapsed, nor refute a separately
restricted fresh-root graph formulation. No AUX solver work is adopted or rerun.
