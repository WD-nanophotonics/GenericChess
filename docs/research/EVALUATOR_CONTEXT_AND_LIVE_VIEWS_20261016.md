# Evaluator contexts and live parent views

**Adopt the small live-parent-copy reuse; retain the full-context cache as a
private feasibility result.** The shipped change uses the existing complete live
state/history copier for the two dynamic owner views. It adds no stateful cache,
result fields, model or default policy. Rebuild Native to obtain the cost change.
Small-board active-feature savings motivate this minimal global implementation;
wider/adverse results and the default-static limits remain below.

The question is whether repeated *complete* evaluator contexts justify storing
derived vectors, compared with a smaller change that reuses the checked runtime's
existing live-state copier. A position digest alone is insufficient: the actual
PENDING position and an accepted transport with one history check flag changed
have the same Native position key but vectors `(5,0,1)` and `(0,0,0)`. The edited
transport is a representation stress case, not a second authenticated trajectory.

The count-only two-root study was executed first: 47/392 and 45/416 feature
extractions repeat with exactly equal full keys. The private cache therefore
stores successful three-integer vectors behind full canonical bytes, including
rules, base/current pieces, hands, auxiliary presence/type/value, side/ply, full
ordered digests and actor/check events. Hash matches always require byte equality.
It resets each query and has 4,096 slots and an 8 MiB stored-key ceiling. A miss,
failed extraction, allocation refusal or full table computes the original value.

These are serial, process-global research tables with explicit Python resets,
not a production cache lifecycle. Per-query API clocks exclude reset/free and
engine construction; whole-batch cost includes both. No cache speed number
establishes complete production caller cost, thread safety or general benefit.

The closed exposed D4 pilot contains 256 actual queries. Complete-pair cache
ratios are heterogeneous, including a dynamic 8-board family benefit and adverse
families. Wider dynamic pairs are censored. Even with 31 hits in 32 direct calls,
the real cyclic-history cache cost ratio rises from .33 at zero plies to 1.31,
3.32 and 5.13 at 128, 512 and 1,023 plies. Those are component timings on a small
fixture, not search speed or population estimates. Full Native storage still
raises the existing Core-directed refusal.

The alternative changes only how the two owner views in dynamic extraction copy
their parent. It reuses the runtime's existing fixed-fields-plus-live-history
copy. Every live history entry and auxiliary field stays available to S3/S4;
only unused array capacity is omitted. Searched children, terminal authority, PV,
rule limits, result fields, evaluators and defaults are untouched by this source
candidate. Component ratios on sixteen exposed roots are .72-.83 on four-board
cases and .94-1.005 on wider cases. Actual full-query transfer remains the test.

Two further measured alternatives inform the next choice. Binding validation
accounts for only roughly 2.5-11% of instrumented feature time, with substantial
timer overhead on tiny cases: no guard-skipping API follows. Semantic attack
tests account for roughly 39-77%, with overhead retained. That justifies a future
bounded exact target/path-index question, not incremental attack caches or
dropping full auxiliary/history semantics. Existing source data support these
diagnoses; neither is a playing-strength result. A subsequent four-state census
actually begins the next step: on one 16-board parent/child, attack testing scans
49,920/52,224 board cells and 32,058/34,071 target occurrences but finds zero
matching target occurrences. A conservative per-type/owner/target/source bitset
would occupy 163,840 bytes there (256 bytes on the four-board control). No index
has been allocated and initialization cost remains unmeasured. These two exposed
families justify a bounded construction-cost test, not a general speed claim.
Any candidate must preserve first-source-entry behavior and every matching target
occurrence, plus runtime path/state/auxiliary guards.

The useful lesson from CHAT suggestions is to measure input cost separately from
model size and utility. [Spatial State-Action Features for General Games](https://arxiv.org/pdf/2201.06401)
shares and orders proposition tests within feature matching, and separates
initialization/memory/runtime measurements from playing-strength experiments.
Its setting permits advance game knowledge and offline training; it does not
establish immediate unfamiliar-rule transfer for GenericChess. This is a source
reading and scoped design inference, not implementation, training or a new
architecture requirement. Our observed history-sensitive vector forbids inferring
that local spatial state is sufficient for the complete target.
